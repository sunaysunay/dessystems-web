Stock Management

Inventory tracking, reservations, and the 60-minute auto-cancel rule

Stock Concepts

TermMeaning
on_handPhysical units at the location (warehouse shelf count)
reservedUnits held for in-flight checkouts and pending orders (reservations are created at checkout, not on add-to-cart)
Availableon_hand − reserved = what can be added to a new cart

Reservation Lifecycle

1. Reserve Customer starts checkout → shop_reserve_stock creates rows with state held and 60-min TTL (adding to cart does NOT reserve stock)
2. Link At checkout → shop_link_reservations attaches reservation to the new order
3a. Payment succeeds → shop_consume_stock sets state committed, decrements both on_hand and reserved
3b. Payment fails / abandoned → shop_release_stock sets state released, units return to available pool
3c. 60 min expires → cron calls shop_release_expired_reservations → state becomes released, stock freed. If linked to an unpaid order in draft/pending_payment, that order is auto-cancelled with a reservation_expired event
⚠
Critical: The 10-minute stock maintenance cron (POST /api/admin/stock-maintenance) must be running. Without it, expired reservations are never cleaned up and available stock shrinks until manually released.

Reservation States

StateMeaningStock Impact
heldReserved, waiting for paymentreserved count increased
committedPaid — stock permanently deductedon_hand and reserved both decreased
releasedManually or automatically freedreserved decreased — back to available
expiredDefined in schema but never set — the TTL sweep marks rows released instead. Don't search for this state when auditing—

The shop_reserve_stock function uses SELECT ... FOR UPDATE to lock inventory rows — two buyers of the last unit cannot both succeed. If available stock is insufficient, that variant's allocation rolls back and any reservations made for earlier cart lines are released by the checkout code. The customer gets HTTP 409 naming the first unavailable SKU.

Admin-Settable States

Admins can directly set an order to any of these 5 states (if the transition is valid):

cancelled on_hold completed paid shipped
ℹ
on_hold is the escape hatch. It can be entered from almost any state and can transition to almost any state. Use it when you need to pause an order for investigation.

Key Rules

  • Same-state writes are idempotent no-ops (won't error)
  • Invalid transitions return HTTP 409 Conflict
  • Terminal states: completed and cancelled — no transitions out
  • Payment webhook moves draft → paid and triggers invoice generation
  • Stock deduction is intended at paid (currently broken — see Known Issues)
  • delivered is NOT admin-settable — it comes only from the carrier webhook

Use on_hold when: a customer requests a change after payment, you need to investigate a suspicious order, a shipping issue needs resolution, or you need to wait for stock from a supplier. From on_hold, you can resume the order to any appropriate state.

No. shipped can only transition to delivered, completed, or on_hold. If a customer wants to return a shipped item, use the Returns flow instead. You can put it on_hold first, then process the return, then complete or cancel from on_hold.

The 14-Day Refund Clock

⏰
CRD Art. 13(1): The refund deadline runs 14 days from the customer's request. The refund dashboard (GET /api/admin/refunds?due=1) flags returns at 10 days after the request with no refund executed. Rule of thumb: refund within 14 days of the request date. Note: the return record also stores refund_due_at = approval + 14 days — when in doubt, use the earlier (request-based) date.

Step-by-Step Procedure

1. Customer requests return via the storefront → state: requested
2. Review & approve/reject Admin PATCH with action transition, target approved. Rejection requires a documented reason (400 error without one). State: approved — but remember the CRD refund clock already started at the customer's request
3. Send return label PATCH action create_return_label → Sendcloud creates return parcel, customer gets email with label URL. State: label_sent
4. Package in transit Track via Sendcloud. State: in_transit
5. Receive package Transition to received — sets received_at timestamp
6. Inspect PATCH action inspect with outcome + notes. Creates inspection record. State: inspected
7. Resolve Transition to refund_approved or rejected. Rejection requires reason. Customer receives email notification either way.

Refund Execution

  • Execute via POST /api/admin/refunds with order_id, amount_cents, reason
  • Withhold gate (CRD Art. 13(3)): Refund is blocked if any return for that order is in requested, approved, label_sent, or in_transit. The gate opens as soon as the parcel is received — inspection is not required before refunding. Override with override_withhold_reason (triggers Telegram alert)
  • Amount capped at: paid amount minus sum of already-pending/refunded amounts
  • Refund executes at Mollie, credit note auto-generated and emailed to customer

Checkout Flow

From cart to order — step-by-step validation and creation

1. CSRF + Rate Limit Validates CSRF token, checks 10 requests/hour limit per IP
2. Validate Inputs Email, billing address, terms_accepted (CRD Art. 8(2) — order not binding without it)
3. Load Cart Fetch active cart by token, load lines with variant pricing
4. Coupon Re-validation Server-side — client-supplied discount is never trusted
5. Reserve Stock 60-min TTL per variant. On insufficient stock → all reservations rolled back, HTTP 409
6. Country Check Queries shop_country_capabilities.can_order — blocks if false
7. VAT Verification If VAT ID provided: VIES check. Failure → charged as B2C (logged for review)
8. OSS Threshold Below €10k EU B2C → NL VAT rates. Above → destination country rates
9. Tax + Shipping Compute totals, fetch eligible shipping methods
10. Create Order Insert shop_orders (state: draft, payment: unpaid), link reservations, insert lines
11. Record Agreements T&C acceptance logged with doc version, SHA-256, IP, user-agent
12. Finalize Consume coupon, mark cart converted, return order details
⚠
If anything fails after stock reservation (steps 6–12), all reservations are automatically released. No stock is lost on checkout errors.

Finance & Tax

Invoicing, credit notes, OSS threshold, and VAT regimes

Invoice

  • Seller: DES Hold B.V., KVK 94872635, BTW NL866349271B01
  • Numbering: gapless DB sequence — voided numbers logged, never reused
  • Immutability: DB trigger prevents mutation of fiscal fields. Corrections only via credit note
  • Generated: automatically when payment webhook confirms order is paid
  • Storage: PDF in Supabase bucket invoices/{order_id}/{number}.pdf
  • Format: bilingual FACTUUR / INVOICE with per-line VAT breakdown

Credit Note

  • Numbering: separate gapless sequence from invoices
  • Generated: automatically on every refund execution
  • Supports line-level partial refunds or proportional distribution
  • References original invoice, linked to refund record
  • Emailed to customer with PDF attachment (nl/en/de)

CSRF Protection

Double-submit cookie: desshop_csrf (SameSite=Strict). All state-changing routes require matching x-csrf-token header. Constant-time comparison via crypto.timingSafeEqual.

Exception: Consent/cookie route — sendBeacon can't set custom headers.

Telegram Alerts

Security events fire alerts to the configured Telegram chat via DesAssistant22bot:

  • Login lockout (5 failed attempts)
  • Admin auth lockout
  • Admin state overrides
  • Refund executions
  • Withhold gate overrides
  • Webhook signature failures

Admin Identity

Set ADMIN_USERS env var as a JSON map: {"username": "Display Name"}. All admin event logs carry the named actor instead of a generic "staff" label.

Known Issues

Confirmed by deep audit (2026-08-21) — operate around these until fixed

🔴
Stock is never deducted on sale. shop_consume_stock is defined but never called by the payment webhook. Paid orders keep their reservations as held and on_hand is never decremented. Until fixed: reconcile reserved/on_hand manually against shipped orders.
🔴
CSRF cookie never issued. The guard is enforced but nothing sets desshop_csrf or sends the header from the client — production POSTs (login, checkout, returns) will 403 until an issuer + client wrapper is added.
🔴
Admin lockout bug. The admin rate limit (5/15 min) counts every admin request, not just failed logins — a normal dashboard session locks you out and fires a false Telegram alert.
🔴
OSS turnover never accumulates. Below-threshold orders are tagged tax_country = 'NL' and then excluded by the NL filter — the €10k threshold can never trip organically and nl_micro orders are missing from the quarterly export.
⚠
T&C not yet seeded. Until a terms document is published via /api/admin/legal, checkout silently skips the agreement record and the confirmation email has no T&C PDF — legal evidence gap on every order.
⚠
Refund-due worklist quirks. Cancelled returns appear on the ?due=1 list (they need no refund) and the two refund clocks disagree (request+14d vs approval+14d). Use the request-based date.
⚠
Concurrent refunds can exceed the cap. Two simultaneous refund submissions can both pass the amount check. Only one staff member should execute refunds for a given order at a time.
⚠
Countries with no matrix row can order. The checkout gate fails open for countries missing from shop_country_capabilities — keep the matrix complete.
